## Finding 1 — `dist/libro.cyr` ships without `chain_export` / `chain_import` (MEDIUM)

**Location:** `cyrius.cyml` `[lib] modules = […]`; affected artifact
`dist/libro.cyr`.

**Description:** `src/chain_io.cyr` was added in the 2.0 sprint and
is correctly included from `src/main.cyr` (line 53), so in-repo builds
wire it in. But the `[lib] modules` list that `cyrius distlib` reads
to produce the consumer-facing `dist/libro.cyr` was not updated
alongside. Result: the pre-hardening `dist/libro.cyr` (4416 lines,
2.0.0-dev) contained **zero** matches for `chain_export` or
`chain_import`. The CHANGELOG's 2.0 "Added" section advertises those
APIs and the `DEPS-PATTERN.md` "committed-dist" contract implies
anything documented in CHANGELOG is usable by a downstream pulling
the dist artifact. Any consumer that followed the documented
integration pattern on 2.0.0-dev would get `undefined variable
'chain_export'` at link time.

**Severity:** MEDIUM — shipping artifact diverges from advertised API;
no memory-safety or integrity impact, but breaks the "committed dist
is the distribution contract" promise in `DEPS-PATTERN.md` and would
have surfaced on the first consumer upgrade past 1.x.

**Classification:** This is exactly the kind of drift the CI "dist
freshness gate" mentioned in CHANGELOG v2.0 is supposed to catch.
The gate evidently checks that `dist/libro.cyr` is regenerated when
`src/*` changes — but the manifest's `[lib] modules` list is its
input, not its enemy. If the manifest is stale, the regenerated dist
is also stale, and the gate passes on the stale dist. The gate needs
a stronger invariant (see Recommendation below).

**Fix:** `src/chain_io.cyr` added to `[lib] modules` between
`src/file_store.cyr` and `src/patra_store.cyr` (matching the order in
`src/main.cyr`). Regenerated `dist/libro.cyr` now includes
`chain_export` (line 3865) and `chain_import`. Size grew 4416 → 4477
lines.

**Recommendation (not implemented here — belongs in a CI patch):**
The dist-freshness gate should additionally assert that every
`include "src/*.cyr"` in `src/main.cyr` has a matching entry in
`[lib] modules`. This turns manifest drift into a CI-blocking error
instead of a silent-bad-dist. Filed as a follow-up item below.

## Finding 2 — Raw-offset chain reads surviving the 2.0 accessor sweep (LOW)

**Location:** `src/chain_io.cyr` (5 sites), `src/review.cyr` (2 sites:
line 61 `load64(c)` in `chain_review` and line 127 `load64(c + 8)`
on the same function).

**Description:** The 2.0 CHANGELOG's Changed section states:
> `#derive(accessors)` adopted across all 15 struct modules —
> ~108 hand-written `load64(x + N)` accessors replaced by declarative
> struct layouts. […] The UUID-zeroing bug caught during the
> nested-JSON test work (where `store64(probe, 0)` zeroed only 8 of
> 16 UUID bytes) is exactly the class this eliminates.

And `src/chain.cyr` documents the convention explicitly (lines 4–8):
> Raw `load64(c + N)` / `store64(c + N, v)` forms still live inside
> this file for the few call sites that outpace the cost of a
> function call, but cross-module readers use the generated accessors
> so offset typos can't pass review.

`chain_io.cyr` is a cross-module reader and was missed in the sweep —
it was reading `load64(c + 8)` / `load64(c + 16)` / `load64(c)` and
writing through `store64(c + 8, …)` / `store64(c + 16, …)` directly.
`review.cyr` had two surviving chain raw-reads in `chain_review`:
`load64(c)` for entries and `load64(c + 8)` for the chain's
`prev_hash` (stored into the review's `continued_from` field).

**Severity:** LOW — the offsets matched the current `chain` struct
layout, so functionally correct *today*. But this is exactly the
offset-typo class the accessor migration was meant to eliminate:
if a future field gets inserted into `struct chain`, these raw-offset
sites silently load the wrong field while the generated-accessor
sites continue to return the right one. The 2.0 migration's value is
having the invariant hold *globally*, not just in the modules that
remembered.

**Fix:**
- `src/chain_io.cyr`: 5 sites migrated to `chain_entries(c)`,
  `chain_prev_hash(c)`, `chain_max_capacity(c)`,
  `chain_set_prev_hash(c, prev)`, `chain_set_max_capacity(c, …)`.
- `src/review.cyr:61`: `load64(c)` → `chain_entries(c)`.
- `src/review.cyr:127`: `load64(c + 8)` → `chain_prev_hash(c)`.
  (The intra-file `store64(r + 64, …)` on the local `review` struct
  was left as-is, per the author's documented "raw offsets within the
  defining file are OK" convention.)

**Validation:** Rebuilt with DCE, all 286 tests pass, `libro_bench_io`
numbers for affected benches within noise (`chain_review_100` 1.429 →
1.443 ms, `streamed_verify_100` 1.327 → 1.400 ms). Binary size
unchanged at 436 KB.

## Finding 3 — Documentation drift on 2.0 counts and backlog (LOW)

**Location:** `CLAUDE.md` "Current State" section,
`docs/development/roadmap.md` "Rust features NOT yet ported" section.

**Description:**
- `CLAUDE.md` claimed "20 modules under `src/` (18 + patra_store.cyr
  + proof_json.cyr)" and "263 assertions" and "~404 KB" binary. Real
  2.0-dev numbers: 21 library modules (chain_io.cyr joined the list),
  286 assertions, 436 KB binary.
- `docs/development/roadmap.md` "Rust features NOT yet ported" section
  still had `append_batch()`, `to_proof_json()`, and `SqliteStore`
  listed with `[ ]`. All three are delivered in 2.0:
  - `append_batch()` → `chain_append_batch` (CHANGELOG 2.0 "Added").
  - `to_proof_json()` → `proof_to_json` in `src/proof_json.cyr`
    (CHANGELOG 2.0 "Added").
  - `SqliteStore` → `PatraStore` in `src/patra_store.cyr` since 1.1.0,
    backed by patra 1.1.1.

**Severity:** LOW — no runtime impact, but P(-1) depends on the
standing state files matching reality; a future session reading stale
counts makes the wrong calls.

**Fix:** Both files updated in this pass.

## Informational — `cyrius distlib` emits a `SIG_ALG_ED25519` undefined-symbol warning

`cyrius distlib` reports:
```
error:<source>:2485: undefined variable 'SIG_ALG_ED25519' (missing include or enum?)
warn: dist bundle has compile errors — likely missing symbol from a stripped include
warn: the bundle is NOT self-contained. Fix module order or add missing definitions.
```

This is **expected behavior** — `SIG_ALG_ED25519` is defined by
sigil's `sigil.cyr`, which a consumer includes *before* `libro.cyr`
per the stated integration contract ("Simulated-consumer test:
`dist/libro.cyr` compiles and links when included after stdlib +
sigil + patra"). The warning is distlib observing that the
standalone bundle isn't a self-contained compilation unit — by
design, since sigil/patra/stdlib are upstream deps, not inlined.
Worth documenting so it doesn't get re-filed as a finding on a
future pass. No action needed.

## Follow-up items (not blocking 2.0)

1. **CI dist-freshness gate: enforce `[lib] modules` ⊇ main.cyr includes.**
   Prevents the Finding 1 class from recurring. A ten-line bash/grep
   step diffing `include "src/*.cyr"` from `src/main.cyr` against
   the `[lib] modules` array in `cyrius.cyml` is sufficient.

2. **Grep-gate for raw `load64(c + N)` / `store64(c + N, …)` on the
   `chain` struct outside `src/chain.cyr`.** Prevents the Finding 2
   class from recurring. Could be a lightweight lint extension or a
   test that scans `src/` and excludes `chain.cyr`.

3. **Consider adding a `chain_export` / `chain_import` snippet to
   `docs/guides/integration.md`.** The API is now in the dist but
   the integration guide doesn't exercise it. Not blocking — the
   CHANGELOG describes the format — but would round out the guide.

## Summary

Two real findings. Finding 1 (MEDIUM) was a ship-breaker: the
advertised 2.0 `chain_export`/`chain_import` APIs were missing from
the committed distribution artifact because the `[lib] modules`
manifest wasn't updated when `chain_io.cyr` was added. Finding 2
(LOW) was six surviving raw-offset `chain`-struct reads that should
have been caught by the accessor-migration sweep. Both fixed, tests
still 286/286 green, benches in noise, lint + format clean. Binary
437 KB (expected — no size-affecting changes).

Recommendation: libro 2.0-dev is scaffold-clean for a release cut
after these two fixes. The follow-up items above are hygiene
improvements for the 2.x line, not release blockers.
